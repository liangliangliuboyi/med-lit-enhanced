# `med-lit-enhanced` 开源化：可行性评估与路线图

> 评估日期：2026-11-05 ｜ 评估对象：本地完善版 `~/.workbuddy/skills/med-lit-enhanced/`
> 定位：上海交通大学医学院学生个人作品，面向医学/公共卫生研究者的循证文献检索 Agent 技能
> 核心问题：**"把自用完善版开源、隐匿密钥、让用户填自己的 key"这件事，可行吗？**

---

## 一、结论

**可行。** 且不需要为"开源"牺牲太多东西——这个技能的技术底座（纯标准库、零第三方依赖、模型/程序职责分离）**天然适合开源分发**。

但有 **3 个前置条件**必须在发布前解决，否则开源出去的是"半成品 + 事故"：

| # | 前置条件 | 严重度 | 说明 |
|---|---|---|---|
| **P0-1** | 密钥必须环境变量化 | 🔴 事故级 | 明文 key 一旦随仓库公开，等于把付费额度送给所有人 |
| **P0-2** | NCBI `tool` + `email` 必须注册并写死为项目标识 | 🔴 合规级 | NCBI 明文要求分布式软件注册，否则违规 IP 会被封禁 |
| **P0-3** | 必须内置 NCBI 免责声明与版权声明 | 🟠 法务级 | NCBI 明文要求"must be evident to users of your service" |

其中 **P0-2 是你目前完全没有意识到的**——它不是"最好有"，是"必须有"，而且 NCBI 的封禁是**按 IP** 的，会连带影响你身边的人。

## 二、五维可行性评估

### 2.1 法律与合规（逐条核对 NCBI 官方政策）

| NCBI 条款 | 本技能现状 | 判定 |
|---|---|---|
| 无 key 限速 3 req/s | 代码节流 0.36s ≈ 2.8 req/s | ✅ 合规 |
| 有 key 限速 10 req/s | 节流不因有 key 放宽，安全 | ✅ 保守合规 |
| 分布式软件需注册 `tool`/`email` | `tool` 有值，`email` **为空** | ❌ **不合规，须修** |
| 请求参数用小写（除 `WebEnv`） | 全部小写 | ✅ |
| 空格用 `+`，特殊字符 URL 编码 | `urllib.parse.urlencode` 自动处理 | ✅ |
| 免责声明须对用户可见 | SKILL.md 无 | ❌ **须修** |
| 摘要版权 | 仓库不含任何 PubMed 内容，运行时下载 | ✅ 无风险 |
| 批量请求建议避开工作日白天 | 单次约 4-6 次请求 | ✅ 远低于阈值 |
| 建议让用户填自己的 API key | 计划正是如此 | ✅ **与官方建议完全一致** |

**额外提醒**：NCBI 的注册邮箱是 `vog.hin.mln.ibcn@seitilitue`（官方文档原文写法），注册邮件需说明开发者姓名或组织名。
一旦开源，"你维护的这个工具"与"任何用它的人"共用你的注册身份——**用户违规会打到你头上**，所以配置里的 `tool` 必须是**项目级标识**而非个人标识。

### 2.2 技术可行性

| 维度 | 现状 | 判定 |
|---|---|---|
| 依赖 | 纯 stdlib，`git clone` 即可跑 | ✅✅ 极大优势（同类项目大多要 `pip install biopython httpx`） |
| Python 版本 | `from __future__ import annotations` 已启用 | ✅ 3.9+ 即可（建议声明 3.10+） |
| 模型可用性 | 实测平台 99 个可用模型，配置中 17 个角色模型 + rerank + embed **全部命中** | ✅ 无需改动 |
| 模型层耦合 | `base_url` 已可配；`/rerank` 是硅基流动特有，但**已有失败降级** | ⚠️ 需抽象（见路线图 P2） |
| 网络可达 | 硅基流动国内直连；NCBI 需境外直连（国内需代理） | ⚠️ 国内用户跑 PubMed 可能需要代理，须写进 README |
| 密钥泄漏面 | `config.json` 明文 | 🔴 须改 |
| 端口/依赖 | 无数据库、无本地服务、无后台常驻 | ✅ 极轻量 |

### 2.3 竞争格局（真实存在的同类项目）

| 项目 | 形态 | 许可 | 规模 | 覆盖缺口 |
|---|---|---|---|---|
| `lit-synthesizer` | Claude Skill（Python） | MIT | 91★ / 18 fork | 英文；引用靠模型自觉；无中文 |
| `PubCrawl` | MCP Server（TypeScript） | MIT | — | 需 npm build；英文；无证据分级 |
| `pubmed-database` × 6+ | Skill（多为提示词壳） | MIT | 单星为主 | 多为"裸 REST 访问"，无流水线 |
| `pubmed-literature-miner` | Skill | — | 300★ 市场页 | 通用，无垂直适配 |

**结论：赛道拥挤，但都停在"能检索"这一层，没有一个做到"中文提问 → 每句挂 PMID → 全流程可审计"。**

**你的差异化定位（三条，缺一不可）**
1. **中文输入 → 中文输出 → 每条实质性论断挂 `[PMID:xxxx]`**，且参考文献由脚本从 PubMed 原始字段生成（模型碰不到期刊名/年份，杜绝编造）；
2. **全流程 10 文件留痕可审计**（检索式、题录、证据、审查意见、trace、耗时、实际命中模型）——**这是循证方法学的要求，竞品全部没有**；
3. **零第三方依赖 + 医学院垂直预设**。

**预期规模的诚实校准**：同类优秀 skill 的天花板是 **百星级、几十到上百 fork**。不要按"爆款"规划，按"一个真被用起来的工具"规划。

### 2.4 "适用于我们医学院"——**这是最大机会，也是当前最大缺陷**

我核对了内置期刊白名单的 26 本：

```
Nature, Cell, Science, Nat Aging, Nat Biomed Eng, Nat Cancer, Nat Cell Biol,
Nat Genet, Nat Immunol, Nat Mater, Nat Med, Nat Metab, Nat Methods,
Nat Microbiol, Nat Nanotechnol, Nat Biotechnol, Cancer Cell, Cell Host Microbe,
Cell Metab, Dev Cell, Immunity, Matter, Med, Mol Cell, Sci Immunol, Sci Transl Med
```

**26 本里 23 本是 Nature/Cell 系列与基础科学刊**（遗传学、免疫学、纳米材料、细胞生物学……）。
对临床医学院学生而言，真正相关的只有 `Nat Med`、`Sci Transl Med`、`Med` 三本。
而 **NEJM、Lancet、JAMA、BMJ、Diabetes Care、Diabetologia、Lancet Diabetes Endocrinol、Ann Intern Med——一本都没有。**

**换句话说：现在这个技能开箱即用的"限定高影响力刊"模式，对医学院场景基本是废的。** 这是开源后会被用户立刻吐槽的第一件事。

**四层"医学院适配"应该做什么（按价值排序）**

| 层 | 内容 | 价值 |
|---|---|---|
| **L1 期刊白名单** | 内置**临床**白名单（Lancet/NEJM/JAMA/BMJ/Diabetes Care/Diabetologia/Lancet Diabetes Endocrinol/Nat Rev Endocrinol/Ann Intern Med/Circulation/JACC/Gastroenterology/Hepatology/…），并保留一份"基础科学"白名单作为可选配置 | ⭐⭐⭐ |
| **L2 PubMed 临床查询过滤** | 比期刊白名单更本质：**PubMed 官方 Clinical Queries**（Therapy/Diagnosis/Prognosis × Broad/Narrow）与 Science-Based Medicine filters，用 PICO 自动套用对应 filter，比"限刊"精准得多 | ⭐⭐⭐⭐ |
| **L3 学科域预设** | 预置 MeSH 检索模板：① 糖尿病/肥胖/代谢病（贾老师组核心方向）② 慢病管理与基层防治 ③ 循证医学与卫生技术评估 ④ 公共卫生与卫生政策。命中预设时自动附加该域的 MeSH 树与年限策略 | ⭐⭐⭐⭐ |
| **L4 循证分级与报告规范** | critic 阶段增加 **GRADE 确定性分级**（高/中/低/极低）；流程阶段输出 **PRISMA 计数**（检出/去重/初筛/全文/纳入/排除及理由）——**这两项是论文与系统评价的硬需求，竞品全无** | ⭐⭐⭐⭐⭐ |

> **最值得做的是 L2 和 L4**：L1 是"选刊"（粗），L2 是"按研究设计精筛"（准），L4 是"论文能直接用"（刚需）。L3 决定"专不专属于医学院"。

### 2.5 现实成本（你个人的投入）

| 项 | 估算 | 说明 |
|---|---|---|
| P0 整改 | 6–10 h | 密钥环境变量化、PMID 校验、并发锁、注册 NCBI、写 disclaimer |
| P1 医学院适配 | 15–25 h | 临床白名单、Clinical Queries、域预设、GRADE、PRISMA |
| P2 provider 抽象 | 8–12 h | sf.py 重构 + 双语配置文档 |
| P3 发布打磨 | 8–12 h | 双语 README、LICENSE、示例输出、镜像同步、首次发布 |
| **合计** | **约 40–60 h** | 分摊到数周，**不需要一次做完** |
| 单次运行模型成本 | 约 ¥0.3–2 | 11 次调用（1 planner + 8 reader + 1 critic + 1 writer）+ 1 rerank，DeepSeek-V3.2 档位 |

## 三、推荐架构：三层分离（回答工作空间问题）

你让我"看完想法再判断要不要换"。**结论：要改，但理由变了。**

原判断理由是"跨空间隔离"；**现在的真正理由是：开源后你需要同时存在三个互不污染的层**。

```
┌─ ① 源码层（git 仓库，可公开）────────────────────────────┐
│  E:\workcreate\med-lit-enhanced\                          │
│    SKILL.md  scripts/  config.example.json  presets/      │
│    README.md  LICENSE  .gitignore  docs/                 │
│  → git remote → GitHub（主）/ Gitee（国内镜像）            │
└───────────────────────────────────────────────────────────┘
              ↑ 开发时编辑这里
              ↓ Junction（改仓库即生效，无需复制）
┌─ ② 已安装层（Agent 运行时读取）───────────────────────────�┐
│  C:\Users\LZY13\.workbuddy\skills\med-lit-enhanced\        │
│    → Junction 指向 ①                                      │
│  → 你在 WorkBuddy 里调用技能，实际执行的是 ① 的代码        │
└───────────────────────────────────────────────────────────┘
              ↑ 读 config.local.json / .env
              ↓ 写出
┌─ ③ 产物层（每次运行的证据，可重建，不入 git）────────────┐
│  E:\workcreate\med-lit-runs\<时间戳>_<主题>/               │
│    01_question.md … 10_trace.json                         │
│  → .gitignore 排除；可随时重跑重建                          │
└───────────────────────────────────────────────────────────┘
```

**这样做的三个好处**
1. **你的"完善版"和"开源版"是同一份代码**，靠 `.env` + `config.local.json` + `presets/` 区分——不会出现"改了本地版忘了同步开源版"的经典坑；
2. **产物永不进仓库**（`runs_root` 可配 + `.gitignore` 双保险），不会误传 PubMed 摘要；
3. **Junction 让"改完即生效"**，不需要每次手动复制 skills 目录。

**为什么不放 `~/.workbuddy/skills/` 直接开发**：那个目录是 WorkBuddy 的技能缓存/同步区，混进 git 仓库会污染缓存，而且它是 Junction 到 `E:\WorkBuddy_cache\` 的，git 操作会很难看。

**注意**：`~/.workbuddy` 本身已是 Junction，`skills/` 里再放 Junction 是合法的（NTFS 支持），但要实测一次确认 WorkBuddy 的技能加载器认 Junction；**若不认，退化为一条复制命令**（`robocopy` 单命令，同步脚本化即可）。

## 四、开源前必须修的清单

### P0 — 阻断发布（必做）

| # | 项 | 具体做法 |
|---|---|---|
| 1 | **密钥环境变量化** | `config.json` → 只留 `base_url` 等非敏感项；key 从 `os.environ` 读，`.env.example` 给模板；`config.local.json` + `.env` 进 `.gitignore` |
| 2 | **NCBI tool/email 注册** | 定一个**项目级** `tool` 标识（如 `medlit-agent`）与**你的**邮箱，向 `vog.hin.mln.ibcn@seitilitue` 发注册邮件；README 写明"改这个请留自己的邮箱" |
| 3 | **NCBI 免责声明** | SKILL.md 与 README 首屏显著位置放 NCBI Disclaimer & Copyright 链接 + 一句话版权提示（摘要版权归出版商/作者） |
| 4 | **PMID 越界校验** | `save()` 前正则抽正文 `[PMID:\d+]`，与候选池求差集，差集非空写进 `trace['errors']` 并告警——这是**唯一能自动发现"模型编文献"的机制**，也是你文档里已经承诺却没实现的功能 |
| 5 | **并发竞态修复** | `fulltext_limit` 判断加锁 + 独立计数器，否则并发下可能超量抓全文 |
| 6 | **产物目录三层分离** | `runs_root` 改默认 `./runs`，你的本地版指向 `E:/workcreate/med-lit-runs` |
| 7 | **死配置清理** | 删 `retrieval.rounds` 或真正实现二轮扩写；`--research-only` 的 400 字硬编码改读 config |
| 8 | **首次 commit 前轮换密钥** | 当前硅基流动 key 与 NCBI key **从未提交过，但一旦建仓就要保证不再进库**；发布前建议直接换一把新的 |

### P1 — 医学院适配（核心价值）

见 §2.4 的 L1–L4。

### P2 — provider 抽象（决定国际用户能否用）

- `sf.py` 抽成 provider 概念：`base_url` + `api_key` + `models` 全在 config，**任何 OpenAI 兼容端点可用**（OpenAI / DeepSeek / Kimi / 通义 / 本地 Ollama / vLLM）；
- `/rerank` 设为**可选增强**：不可用时自动跳过（现有降级已支持），README 说明"无 rerank 也能跑，只是排序变粗"；
- 给出**两套开箱配置**：国内用户（硅基流动）、国际用户（自填 OpenAI 兼容端点）；
- 明确告知国内用户：NCBI 需境外直连/代理。

### P3 — 发布物料

- 双语 README（中文为主、英文为辅）；
- `LICENSE`（建议 **MIT**，最利于被复用；若希望衍生改动也公开则 GPL-3.0）；
- `CONTRIBUTING.md`；
- 一份**脱敏的真实运行示例**（把 `06_fulltext/` 和含隐私的题录剔除后再放）；
- **品牌与免责**：README 写明"由上海交通大学医学院公共卫生学院学生个人开发，非学院官方产品"——**避免暗示官方背书**；
- GitHub 主仓 + Gitee 国内镜像；
- 可选：同步到 skill 市场（LobeHub / claude-skills 类目录），这是这类技能的主要曝光渠道。

## 七、需要你决策的四点

1. **医学院适配的主轴**：糖尿病/肥胖/代谢（贾老师组核心方向）优先？还是做"循证医学通用底座 + 可插拔域预设"，让各专业自己加？
2. **模型层抽象深度**：锁死硅基流动（国内用户最顺，出问题最好排查）？还是做完整 provider 抽象（国际用户可用，但多一层复杂度）？
3. **是否把成果纳入课题组**：如果贾老师组愿意背书，这个工具可以按团队产出推进（对导师是"AI 糖尿病管理/循证工具"的可见成果，对你个人是强 CV 项），甚至可发展成一篇方法学短文。**要不要走这条路？**
4. **发布时机**：我建议**先内部用满 2–3 个月**再公开；如果你有外部压力（比如时间节点、评奖材料），我们就把 P0+P1 压缩到两周内做完，抢一个"学期初发布"的窗口。

## 八、一句话总评

> 这件事**可行，且值得做**——因为它恰好站在"技术上早已成熟（零依赖、可复现、可审计）、生态上却几乎无人认真做（竞品停在检索层）、需求上有明确人群（中国医学生做系统评价/开题综述）"的交叉点上。
> 但它**不该现在立刻发**：先把密钥、NCBI 注册、PMID 校验这三件"发出去就收不回"的事做完，
> 再把"临床白名单 + Clinical Queries + GRADE + PRISMA"这四件"决定它是不是医学院的"东西做完。
> **前者是安全底线，后者是差异化护城河——两件都不能省。**
